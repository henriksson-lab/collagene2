# Retained cloning runs

`collagene_core::run_lineage::record_run` captures a freshly reconstructed plan as an immutable, versioned `cloning-run-v1` workspace attachment and one new document/history event per operation. The source workspace is borrowed; all additions are staged in a clone and validated before returning `RunCommit`. A capacity failure leaves the original unchanged. Repeating the same capture returns the existing run without adding documents.

Each plan input requires its own `InputEventBinding { input_id, event: EventBinding { document_id, event_id, revision } }`. Equal content revisions in different documents or events are deliberately distinct choices. The independently bound target uses a separate `EventBinding`. It becomes a product parent only when the operation explicitly uses it through a declared input. Historical retained source events are allowed; navigation stacks, source heads, and the active document stay unchanged.

The capture calls the current deterministic verifier. Every step must reconstruct, and the final sequence, orientation and topology must match the independent target (circular rotation is allowed). By default the report must be `ConsistentUnderAssumptions`. Explicit `allow_incomplete` permits a fully reconstructed, matching candidate whose remaining model limits are reported. An incomplete or failed prefix cannot be captured. All current operations, including tracked generation, checked digest, tailing and profiled overlap, use the same source-role resolver. Each operation may declare at most 128 sources; oversized arities are rejected before reconstruction. Duplicate exact parent events are retained once, preserving operation source order.

A run has a full 64-character BLAKE3 ID over its schema, plan, exact input and target roles, product revisions and recorded assessment. Product document IDs derive from the run ID and step index, with deterministic suffixes for existing-ID collisions. Events bind the run ID, operation position, product revision and exact source event parents. Product molecules remain in the workspace revision store; attachments contain their bindings rather than duplicate product snapshots. The plan retains its independently bound source snapshots, options and intended target revision.

New run schema-version-1 records use plan schema 8. Historical plan-schema-3 through 7 records remain readable with their recorded engine. Tracked operations and science-8 assessments require at least plan schema 4; explicit terminal declarations and science-13 assessments require plan schema 8. A native archive with an older outer plan schema cannot contain these records. Each record is limited to 32 MiB, with at most 128 runs per workspace, in addition to the existing workspace document, history, attachment and expanded-byte limits. Plans remain limited to 1,000 operations and 1,000 inputs. Finding strings are limited to 64 KiB, with at most 10,000 findings and 1,000 assumptions. Unknown fields, invalid references and noncanonical IDs are rejected.

`Workspace::validate`, native load and native save validate attachment hashes, schema, run identity, exact event/revision references, source snapshots and declared parent edges. This is structural validation and does not rerun scientific calculations on autosave. A recorded assessment is untrusted historical producer evidence. Editing a serialized attachment cannot establish physical source chemistry or grant verification authority; the verifier still reconstructs physical intermediates from an explicit graph.

`replay_run` explicitly calls the current verifier with the bound source snapshots and independent target, and returns a fresh report together with product-revision, status and engine comparisons. Older engine records remain loadable historical evidence. Replaying them does not alter their recorded producer claim. Persisting or restoring a record never restores a positive verification cache.

`workspace_fingerprint` validates the workspace and hashes a bounded streaming descriptor of names, active state, document navigation, revisions, history, candidates and attachment metadata. Content-addressed revision and attachment keys bind their validated contents, avoiding JSON expansion of binary attachments. Worker results carry the source fingerprint so callers can reject a result if the workspace changed while the calculation ran.

Public helpers include `list_runs`, `load_run`, `load_run_record`, `save_run_record`, `RunCommit::validate`, `ReplayReport::validate`, and `ReplayReport::validate_for_workspace`. The last helper additionally binds report comparisons, plan/target revisions and recorded assessment to the source workspace without repeating scientific calculations. The actual fresh reconstruction occurs exclusively in `replay_run`.
