# Shared lab library storage

`crates/lab-library` provides a native embedded SQLite database for a server-hosted,
shared plasmid folder tree. It has no scientific-core dependency and requires no
external database executable. SQLite is bundled through `rusqlite`; the Rust API
works on Windows, macOS and Linux. Browser clients use the separate binary library
protocol through a trusted host adapter; they never open the database file.

This crate is registered in the main workspace. It provides the durable storage
layer; [the native host](LAB_LIBRARY_HOST.md) validates documents and
[the server](SERVER_LIBRARY.md) supplies authenticated HTTP transport.

## Trusted host boundary

The host authenticates the request and establishes current lab membership before
calling `Library::trusted_host_access`. `LabAccess` is a non-serializable server
capability. Its constructor does **not** authenticate anyone: possession of the
native `Library` handle is reserved for trusted server code. Never derive access
from a client-supplied member name, lab ID, cookie contents without verification,
or payload metadata. Recheck membership for requests after revocation; do not let
long-lived cached access handles bypass the host's membership policy.

All current members share the lab tree. The host binds each request to one lab;
all folder/document/revision operations require that scope. Cross-lab lookups
return `NotFound`, and composite foreign keys additionally prevent cross-lab
parent links. There are no user-private folders, ELN, stocks, freezer records or
organizational reports in this database.

The host must validate every write with the appropriate native loader:

- `protocol::load_document` for `NativeDocument` (maximum 32 MiB).
- `workspace::load_workspace` for `WorkspaceArchive` (maximum 64 MiB), including
  its history, revision references and retained run evidence. Verify the exact
  selected native document, molecule revision and optional head event against
  the decoded archive; do not identify a plasmid by its display name.

Workspace sharing requires an explicit declaration: `DocumentClosure` means the
host has approved a document/dependency closure, while `ExplicitWholeWorkspace`
means sharing the complete archive was deliberately authorized. A selected
plasmid pin alone does not prevent unrelated-data exposure. Never silently upload
an entire local browser workspace while presenting the operation as saving one
plasmid. Preserve required ancestry and evidence in an approved closure; do not
flatten saved material to a sequence-only snapshot to simplify storage.

The storage layer checks payload kind, selection/sharing shape, size and BLAKE3
integrity. It deliberately does not parse native scientific records. A byte hash,
archive, historical report or database entry does not confer physical-material
authority: ordinary fresh native verification and explicit saved-origin replay
remain necessary for downstream cloning.

## Data and concurrency

Lab, folder and library-document IDs are generated by the database using 128
random bits, with `lab-`, `fld-` and `doc-` prefixes. They are stable across renames,
moves and restarts. The root is virtual: a `None` parent/folder means the lab root.
Names are display strings, never filesystem paths. Sibling folders and documents
share a case-sensitive name namespace. Whitespace-only names, controls, names
over 256 characters or over 1024 UTF-8 bytes are rejected.

Each document head points to an immutable revision containing:

- exact binary payload bytes and their separate BLAKE3 archive hash;
- selected native document/revision/event and sharing declaration when required;
- parent revision, monotonically increasing revision number and creation time.

Revision IDs are 64 lowercase hex characters. Their domain-separated BLAKE3 hash
binds the library document ID, parent revision, archive hash, payload kind and
selection/sharing metadata. They are **not** interchangeable with molecule
revisions or archive hashes. Saving identical bytes again creates another
parent-linked event; restoring old bytes does not rewrite old history. Revision
listing is newest first.

`save` accepts an exact `base_revision`. Under `BEGIN IMMEDIATE`, it compares the
current head, inserts the immutable revision and changes the head in one
transaction. A stale writer receives `Conflict { expected, actual }`; it adds no
history or archive bytes and changes no head. Keep both client edits available
and ask the user to resolve divergent changes; do not automatically retry with a
new base revision. Database triggers prohibit revision updates and deletions.

Folder/document rename and move operations use a separate entity generation CAS.
Entity generations start at 1, while an empty lab's catalog generation starts at
0. Content saves also increment the document generation. There is no combined
content-and-metadata save; the host must make any multi-operation behavior clear.
Every successful mutation increments the lab catalog generation.

Browse and name-search pages contain a combined, bounded list of folders and
documents ordered by `(name, id)` using binary lexical order. Subsequent pages
must carry the first page's catalog generation. Any intervening mutation returns
`CatalogConflict`; restart pagination instead of silently skipping/duplicating
items. Revision pages use the same snapshot convention. Name search treats `%`
and `_` literally and uses SQLite's ASCII case folding; non-ASCII text remains
intact, without claiming Unicode case equivalence.

Every write validates parent ownership and ancestry inside its transaction.
Moves reject cycles and preserve the complete subtree. Only empty-folder deletion
is available; there is no document deletion, recursive folder deletion, lab
deletion or history pruning API. Rejected moves/deletions leave data unchanged.

## Bounds and deployment

The database enforces a maximum folder depth of 128, 100,000 folders/documents per
lab, 10,000 revisions per document, 200 entries per page and the native payload
bounds above. `StorageOptions::max_lab_archive_bytes` sets the total retained
archive-byte quota per lab, defaulting to 1 GiB. This is a ceiling, not a
preallocation. Every immutable revision is charged, including repeated identical
bytes; charges and writes are atomic. Quotas do not include SQLite indexes/WAL
or filesystem overhead, so the host also needs normal deployment disk monitoring.
All handles serving the same database must use the same deployment quota.

SQLite uses foreign keys, WAL, `synchronous=FULL` and a five-second busy timeout.
The file must reside on local storage with working SQLite locking, rather than a
shared network filesystem. Multiple native connections/processes can share the
same file; writes serialize and reads use SQLite snapshots. Opening an unrelated
SQLite database or an unsupported schema version fails instead of guessing a
migration. Current application/schema identity is `CGLB`/1.

The server administrator chooses and protects the database location. User-visible
folder names never control paths. Restrict filesystem access to the trusted host
and administrators. A live WAL database includes its sidecar files: use SQLite's
supported backup approach or stop all connections before copying database files;
copying only the main file while writers are active can lose committed data.
The native [operator backup/verify/new-destination restore](LAB_LIBRARY_BACKUP.md)
commands now use SQLite online snapshots and checked immutable manifests; they
never replace an existing live database. Future schema migrations must be explicit
and transactional.

## Validation

`tests/storage.rs` exercises lab isolation, cycles, nonempty deletion, sibling
names, metadata CAS, binary archive/selection persistence across reopen,
simultaneous stale saves on two native connections, snapshot pagination and scoped
literal search, transactional byte quotas, depth/subtree bounds, refusal of
unrelated databases and immutable revision triggers. Fixtures are opaque storage
bytes and intentionally make no scientific-validity claim; host-loader integration
requires its own tests with actual native documents and history archives.
