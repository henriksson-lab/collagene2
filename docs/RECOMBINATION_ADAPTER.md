# Reference recombination adapter

`core::recombination` adapts the independent `collagene-recombination` library to native core documents. The engine remains independent of core, UI and external programs. These are source-derived reference designs; no duplex, phosphorylation, nicks, methylation, host, selection or reaction efficiency is established.

The full F15 goal includes additional scientifically justified profiles/reactions and user workflows. This adapter preserves a complete result for the currently defined two-event att1/att2 reference model, rather than claiming universal Gateway support. See the [scientific engine documentation](../crates/recombination/README.md) for primary manufacturer sources, full-context scope and limitations.

A caller supplies two ordered `reference::Input` records with distinct roles and a `Request`. `ProfileSnapshot` contains the complete exact profile plus its validated content revision; the manufacturer-context profile is an explicit opt-in constructor, not an implicit default. Custom profiles remain caller-declared hypotheses. Request identity covers exact source roles/molecular revisions, profile, reaction, scientific limits and annotation policy. Any change invalidates earlier component selections.

`source_preflight`, `source_target_preflight` and `borrowed_preflight` validate borrowed native models before callers clone source documents. They reuse the engine's bounded native model-tree/text guards. `batch_revision` is the separate adapter-domain binding. Annotation processing additionally charges cumulative work, feature-copy estimates and source-feature counts before projection or fallback cloning. Its report has a separate maximum serialized size. Capacity failure returns an error without publishing partial documents.

`simulate` retains the untouched library `Report`, including every candidate/component, actual source segments, co-sourced overlap evidence, site uncertainty, unsupported geometry, work counters and applicability limits. A separate `ProductDocument` row annotates each reference component. Candidate and component IDs are selectors, not biological winner labels; classic reactions have two products, while the supported linear case may have three.

`Selection` pins the adapter batch plus candidate/component IDs. `product` always reconstructs freshly from the supplied sources/profile/options. It accepts no stored product or report as authority. `check_target` returns the engine's complete target assessment, including possible sites, unsupported geometry, ambiguous source/target DNA, profile-only search completeness and restricted no-match semantics. `checked_product` independently checks the caller's supplied target and requires a fully specified DNA match for the specifically selected candidate/component. Matching another reciprocal product is insufficient. Circular rotation is supported; reverse-complement equivalence requires the caller's explicit policy. These checks establish reference/model consistency only.

`RecombinationReport`, `ProductDocument`, `TargetAssessment` and `CheckedProduct` provide bounded structural/current-binding validators. Those validators do not rerun the scientific engine and never authorize an imported positive claim. A fresh product/check API call is required for release.

## Annotation mapping

The adapter uses `annotations::project_features_with_topology` separately for each parent, using the engine's exact reference segments. Coordinates retain source orientation and circular-origin order. Fully retained continuous features preserve their biological extraction; partial/disrupted locations receive the existing review flags and lose stale translation/frame assertions.

The seven-base crossover overlap is also mapped from both parents where the engine explicitly records identical co-sourced bases. These annotation-only maps are recorded separately from once-only reference DNA segments. They do not duplicate source DNA in the reference conservation calculation and do not claim physical-strand ancestry. A source position that would map to conflicting destination coordinates is unsupported. Features intersecting newly added co-source maps are flagged for review and lose translation/frame assertions.

Unresolved annotations remain reviewed original-source evidence. If a parent's projection cannot be represented safely, the adapter retains that parent's original features as reviewed `unmapped_features` in `SourceAnnotationEvidence`, with exact source role/revision and a reason; it does not invent destination coordinates. Other parents can still contribute projected annotations. The current fallback is conservative at whole-parent granularity: one unsupported coordinate-bearing qualifier can withhold that parent's otherwise projectable annotations. The immutable source graph and evidence allow a future per-feature projection extension without silently discarding the source record. Features wholly outside a component are counted as dropped from that component, not asserted deleted globally; the complete reciprocal report remains available.

## Provenance and chemistry boundary

The output Molecule has newly constructed metadata, no inherited original GenBank or parent metadata, an explicit `recombination:reference_only=true` marker, and the existing restrictive `source:legacy:chemistry_unmapped=true` guard. That guard is reused to prevent `Duplex::from_molecule` from silently assigning an intact-duplex model to the reference preview. Its legacy-named key does not claim a legacy file source. `tracked_modifications` and `duplex_model` are not propagated.

`recombination:unverified_recipe` records the full pinned request, ordered source identities, selected component, all reciprocal component identity summaries and reference product revision. It is reproducibility/provenance data; deserializing it cannot restore a chemical state or passing verification result. Original source documents remain necessary for unmapped annotations and attachment evidence. Future native history and typed-plan integrations must use the existing exact source-event lineage and keep reference-only physical incompleteness sticky.

Text formats cannot preserve the entire report/source graph. A selected component must retain an explicit unverified reference-only marker and export-loss warnings when GenBank/EMBL support is connected; plain FASTA cannot carry those semantics. Keep the native source graph and full report alongside text exports.

The typed-plan integration additionally bounds a plan to64 reference-recombination steps and32MiB total plan-input bases, and runs the shared borrowed native model guard on all input/target documents before plan hashing. A reference-recombination step selects one component while keeping reference-only lineage sticky: downstream PCR or annealing cannot silently regenerate chemical authority from that step.

The text adapter uses an exact generated COMMENT/CC reference-only marker and bounded producer-recipe chunks. Reimports retain these only as `source:recombination:*` historical claims plus the restrictive chemistry-unmapped guard; a feature note cannot activate the marker, and a retained recipe cannot restore a passing reaction check. A generic chemistry-unmapped marker survives even without a recipe. Full reports, source graphs and large recipes can exceed text-format evidence capacity, so retain the native workspace and inspect export-loss warnings.

Current report binding checks each document's bounded recipe against the exact Request and its annotation evidence/recipe identities against the actual ordered source roles and molecular revisions. Expected source revisions are computed once per report binding call, rather than rehashing source DNA for every reciprocal component. A self-consistent imported recipe/evidence pair with foreign provenance still fails the current binding check.

Standalone component validation binds its actual sequence/topology to the annotation-free engine Molecule identity, using the deterministic engine component name. Projected/reviewed counters must equal the actual current feature counts, and current-source binding checks that each parent's mapped+dropped+unmapped count covers its source features exactly. Checked-component binding also compares the actual selected DNA to the independently supplied target under the declared topology, circular-origin and reverse-complement policy. Those cheap consistency checks still do not make a self-consistent imported recipe a fresh reconstruction proof.

Target-assessment shape validation rejects contradictory no-match, search-completeness, applicability, uniqueness and uncertainty fields. Current bindings compare the ambiguity flags directly with actual source and target DNA. No-match claims and self-consistent raw-product hashes remain historical evidence until fresh reconstruction; cheap guards deliberately do not replay the attachment-site search.
