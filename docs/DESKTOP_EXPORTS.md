# Native file exports

Desktop exports use appended DTQ schema 1 `ExportFile` and DTR `Exported` variants. Historical operation/success tags remain unchanged. The request contains only a suggested basename and at most 64 MiB of bytes; it cannot select a directory, absolute path, native identity, or arbitrary filesystem operation. Separators, drive prefixes, control characters, and empty names are rejected. Success binds the actual generated basename, BLAKE3 hash, and exact byte length to the request. Biological file bytes are written unchanged; no newline, encoding, or metadata conversion is performed by native persistence.

The shell creates a `DesktopExports` capability from `DesktopHost::open_exports()` after opening the operator-configured private root. Its only output directory is `<configured-root>/exports`. The frontend gets a basename receipt, never a raw native path. Each operation has a collision-safe, portable filename prefixed with its random operation ID. Names are bounded; Unicode or unsupported filename characters map conservatively to underscores. The suggested-name portion is capped at 180 characters, retaining a short exchange-format extension when truncation is necessary. Exports are never overwritten, automatically opened, or sent to another application.

The export service runs in its own blocking admission lane and uses directory capabilities for all export-file access. It does not take the working/editor host mutex, perform network requests, or share the slow remote-sync lane. Lane selection borrows an untrusted DTQ prefix only; the chosen blocking service independently validates the complete frame, checksum, command, and branded window capability. Small exports are correctly deferred by the cancellation/status fast path. The existing approved local-window/origin rule and single raw `collagene_rpc` ACL apply; there is no filesystem plugin or new remotely callable command.

A scoped job accepts immediately before persistence. Cancellation/revocation before acceptance prevents a write. After acceptance, cancellation does not claim rollback: the bounded native write finishes and its actual outcome is retained. The export lane remains owned by the blocking task even if its IPC caller disappears. Working-file saves and their own CAS continue independently.

Each operation reserves a private immutable intent under `exports/.operations/<operation-id>/intent.json`. It records the exact suggested name, generated basename, payload hash, length, and receipt format version. A flushed temporary receipt is published atomically without overwriting an existing intent. A changed intent under the same operation ID is rejected even after restart or through a separate native connection. Payload bytes are fully written and flushed to a private temporary file before atomic no-overwrite hard-link publication. The published file is read back, hash/length checked, and flushed through that same opened no-follow handle before success; directory handles are also synced on Unix.

Retries after a process restart verify the same persisted intent and stable filename, producing a fresh request-bound receipt without creating a duplicate output. Missing outputs can be recreated only from the same exact request bytes. Partial, corrupted, symlinked, or unrelated existing outputs are never accepted as a successful export or overwritten. Temporary cleanup retains the creation handle: Unix compares the observed entry device/inode before unlinking, and Windows permits delete sharing for hard-link publication and marks only the exact retained creation handle for deletion after publication; a replacement pathname cannot redirect that handle. Observed replacement files are preserved. This is not a sandbox against concurrent actions by the same OS user. Temporary files owned by a completed attempt are removed; abandoned temporary files from a killed process are ignored, never interpreted as valid payloads. A mismatched published file needs explicit operator review/removal; the service does not silently repair it. Retained intent receipts intentionally prevent an operation ID from being repurposed.

Directories are created with mode 0700 and files with mode 0600 on Unix; existing Unix ownership/permissions are checked. Windows inherits the host's user-private AppData/configured-directory ACL requirement. Filesystems must support same-volume hard links and atomic no-overwrite publication; unsupported filesystems return an explicit persistence failure. Windows file `sync_all` flushes file data, while portable directory power-loss durability is unavailable there. Unix directory sync improves namespace durability but cannot override filesystem/device guarantees. Successful receipts acknowledge exact written, flushed, read-verified bytes; they do not promise survival beyond those OS/filesystem guarantees after sudden power loss.

Receipts are small and contain no source data or credentials. The host's bounded shared operation cache accelerates exact retries; the immutable filesystem intent and verified output remain authoritative after restart or cache eviction. Storage errors are sanitized. No raw filesystem paths or OS diagnostic strings are returned to the frontend. Exported biological files and hidden intent metadata stay under the configured root; no external executable participates.

Focused protocol fixtures cover append-only tags, small-control deferral, exact receipt binding, malformed names and bounds. Native fixtures cover exact mixed/binary bytes, restart/idempotent retry, changed intent, mismatched partial/foreign files, ignored orphan temporaries, cancellation before acceptance, independent editor-lock progress, concurrent connections, private modes, and symlink refusal. These are headless backend tests; actual platform export acceptance and GUI workflows remain separate checks.
